Agent 开发如何使用沙箱？两种方式，一次讲清

Kepler452Byte2026/10/31大约 9 分钟AIAgent沙箱架构MCP

当 Agent 开始执行代码、安装依赖、修改文件时，一个问题很快就会出现：这些操作应该在哪里发生？

直接在应用服务器上执行，可能影响服务文件、共享依赖和业务凭据。为任务准备独立的计算环境，是一种常见做法。这个环境可以提供文件系统、终端、进程和网络，也可以按需要配备浏览器；它不一定有桌面，也不一定是一台虚拟机。

但“接入了沙箱”还不足以说明架构。有人让 Agent 调用沙箱中的工具，有人把 Agent 程序本身放进去运行。这两种方式隔离的对象不同，也会改变平台与 Agent 的分工。

区分它们，可以先看一个位置：负责调用模型、决定下一步并执行工具的 Agent 主循环，运行在哪里？

一、让 Agent 调用沙箱

第一种方式中，Agent 主循环运行在应用后端、用户本机或其他外部服务。遇到需要执行代码、操作文件的步骤时，再调用沙箱中的能力。

例如，用户要求分析一份表格并生成图表。Agent 在外部理解任务、生成 Python 代码，把代码和文件交给沙箱执行。获得结果后，它可以修改脚本、重新执行，最后组织回答并交付图表。

沙箱在这里承担的是工具执行环境的职责。Agent 的规划、模型调用和会话管理仍然留在外部。沙箱返回一次操作的结果，是否继续、下一步做什么，由外部 Agent 决定。

这类设计的重点，是为连续操作提供合适的工作区。前一步下载的文件，后一步需要读取；刚安装的依赖，下一条命令可能还要使用。因此，需要明确哪些调用共享环境，以及环境什么时候创建、保留和销毁。

共享文件系统不意味着每次命令都保留当前目录和环境变量。是否支持连续终端会话，需要由具体接口约定。环境服务还要处理调用者归属、超时与回收，不能只依赖 Agent 最后主动调用“关闭沙箱”。

如果希望这些能力被不同 Agent 客户端使用，可以将创建工作区、执行命令、读写文件等操作封装为 MCP Tools，形成独立的沙箱工具服务。

这里要分清两层职责：MCP 统一客户端与工具服务的交互方式，实际隔离由后面的沙箱实现提供。它不会决定 Agent 如何调用模型，也不会自动管理 Agent 主循环。MCP 官方架构说明对此有明确的协议边界。

直接使用 SDK 或 HTTP API 也能实现这种架构。是否采用 MCP，是工具接入方式的选择；主循环在沙箱外，才是这一用法的关键。

二、让 Agent 运行在沙箱里

第二种方式，是把 Agent 程序及其依赖一起放进沙箱。外部平台提交任务、启动执行，沙箱内的 Agent 自行调用模型、执行工具并推进任务。

Agent 主循环

调用模型 · 决策 · 编排工具

↓ 调用工具　↑ 读取结果

工具执行环境

这里的“Agent 运行在沙箱里”，指负责推理与工具编排的程序在里面运行，不意味着大模型也部署在沙箱内。Agent 仍然可以调用外部模型 API。

例如，一个代码任务需要特定版本的 Agent SDK、编译器和测试工具。将这些依赖准备到固定镜像中，可以让 Agent 的执行环境与平台服务分开管理，再按任务分配独立工作区。

这时，沙箱承担的是Agent 执行环境的职责。外部平台面对的是一个可启动、可观察、可取消的执行单元，而不是逐条替 Agent 调用命令。

Agent 进入沙箱后，事件仍然需要传出来。用户需要看到回答文本、工具调用、任务进度与结果，平台也需要知道执行是否正常。

一种轻量方案，是让 Agent 输出结构化 JSON 事件，通过进程 stdout 流传给外部平台；另一种方案，是在沙箱内提供服务接口，通过 HTTP 流、SSE 或 WebSocket 通信。具体传输方式可以不同，但都需要把事件与执行身份关联起来。

例如，同一次工具操作的开始与结果必须能够对应；每段文本增量要归属正确的模型调用；任务完成、失败和取消要有明确语义。客户端收不到输出，不代表 Agent 已停止；进程退出，也不直接证明任务完成。

文本增量与 token 用量同样需要区分。前者用来持续展示内容，后者来自模型实际返回的统计，可能只在一次调用结束时更新。

平台与 Agent 的分工也要清楚：平台负责用户身份、执行授权、任务记录和事件存储；沙箱内 Agent 负责自己的推理、工具编排和工作区操作。如果需要恢复执行，还要进一步约定会话、checkpoint 与环境的关系。

把 Agent 放进去，解决了执行位置与依赖隔离的问题。任务如何管理、事件如何解释，仍然需要平台与 Agent 之间的执行协议来承接。

三、两种方式，怎么选？

两种方式都能执行代码、操作文件，也都可以完成复杂任务。区别主要在于主循环的位置，以及外部系统管理的是工具环境，还是完整的 Agent 执行。

维度Agent 调用沙箱Agent 运行在沙箱里
Agent 主循环在沙箱外在沙箱内
沙箱主要承载工具操作与工作区Agent 程序、依赖与工具操作
外部系统调用命令、文件等工具接口Agent 任务执行接口
主要返回内容工具输出与产物Agent 事件流、结果与产物
管理重点工作区归属与工具生命周期Agent 执行状态与环境生命周期

如果已有一套 Agent 主循环，希望补充终端、文件和代码执行等隔离能力，可以先采用第一种方式。工具服务稳定后，再考虑是否通过 MCP 提供给更多客户端使用。

如果需要独立管理 Agent 的依赖、版本与执行资源，或者希望按任务运行不同的 Agent 实现，可以采用第二种方式。此时应优先明确任务输入、事件输出、取消和结束语义。

两者也可以组合。沙箱内的 Agent 可以调用另一个沙箱工具服务，将依赖冲突或需要额外隔离的操作交给独立环境。但多一层环境，就多一组文件传递、凭据分配与资源回收问题；已有环境够用时，无需提前增加这一层。

最后，还需要保留两条边界。隔离能力取决于实际机制与配置，容器、虚拟机、网络和挂载权限都有各自的约束，不能仅凭“用了沙箱”推断完整的安全保障。

执行可靠性也需要单独设计。 保留文件不等于保存 Agent 的执行状态，保留日志不等于具备可恢复的 checkpoint。任务中断后如何继续、重试会不会重复产生业务副作用，都不是创建一个沙箱就能自动解决的。取消沙箱也无法撤销已经完成的外部业务操作。

选择架构时，先回答三个问题就能缩小范围：Agent 主循环放在哪里，需要隔离哪些能力，运行过程由谁管理。两种沙箱用法，就是围绕这些边界形成的不同分工。
